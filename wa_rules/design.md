# DB 설계 리뷰 가이드 (범용)

이 문서는 DB 설계 리뷰 시, "사용 편의"보다 "물리적 사실과 도메인 진실"을 우선하는 기준을 정리한 가이드다.

## 1. 핵심 원칙

- DB 레이어는 **사실(Fact)과 상태(State)** 를 보존하는 계층이다.
- "사람이 쓰기 편한 형태"는 DB가 아니라 **서비스/조회(데이터 가공) 레이어**에서 만든다.
- 특정 조직/팀(OPG 등)의 현재 운영 편의에 맞춘 구조를 기본 모델로 삼지 않는다.
- "현실의 제약(현재)"과 "이상적인 모델(있어야 할 상태)"을 분리해서 본다.
- 리뷰의 목적은 "지금 동작"이 아니라 "시간이 지나도 무너지지 않는 모델"을 만드는 것이다.

## 2. 안티패턴 (리뷰에서 경계할 것)

- 서비스 레이어의 관심사(화면 표시, 임시 분류, 운영 편의)가 DB 스키마에 직접 들어감
- 한 조직/한 프로세스 기준으로만 이해되는 컬럼/테이블 명
- 의미가 모호한 상태값, 중복 의미를 가진 컬럼
- "조회 편의"를 위해 원본 사실을 훼손하거나 섞어 저장
- 아직 합의되지 않은 정책을 영구 스키마로 고정

## 3. 리뷰 체크리스트

### 3-1. 도메인 정합성

- [ ] 테이블/컬럼이 도메인의 "사실"을 직접 표현하는가?
- [ ] 용어가 유비쿼터스 언어와 일치하는가?
- [ ] 이벤트/상태/결과가 혼합되지 않고 분리되어 있는가?
- [ ] 한 컬럼에 두 가지 의미(시간+상태 등)를 동시에 넣지 않았는가?

### 3-2. 레이어 책임 분리

- [ ] DB 설계에 서비스/화면/운영 편의 로직이 섞이지 않았는가?
- [ ] 조회 편의 요구는 View/Query/애플리케이션 레이어에서 처리하는가?
- [ ] DB는 원본 데이터 보존, 가공은 상위 레이어에서 수행하는가?
- [ ] "지금 사용자에게 편한 형식"을 영구 저장 스키마로 강제하지 않는가?

### 3-3. 확장성과 변경 내성

- [ ] 특정 팀/업무(OPG 등) 변경이 전체 스키마 파괴로 이어지지 않는가?
- [ ] 신규 정책 추가 시 컬럼 재해석 없이 확장 가능한가?
- [ ] Null/기본값/코드값 의미가 장기적으로 안정적인가?
- [ ] 미래 시나리오(채널 추가, 상태 분기 증가, 정책 변경)를 흡수 가능한가?

### 3-4. 무결성과 정규화

- [ ] PK/FK/UNIQUE/NOT NULL 등 제약이 비즈니스 불변식과 맞는가?
- [ ] 중복 데이터 저장이 의도된 캐시인지, 설계 결함인지 구분되는가?
- [ ] 삭제/수정 정책(소프트 삭제, 히스토리 보존, 감사 추적)이 정의됐는가?
- [ ] 트랜잭션 경계와 동시성 충돌 시 데이터 일관성이 보장되는가?

### 3-5. 운영성과 관측성

- [ ] 장애 시 원인 추적 가능한 키(생성시각, 변경시각, 주체, 버전 등)가 있는가?
- [ ] 배치/재처리/백필 시 안전한 식별자와 순서 기준이 있는가?
- [ ] 인덱스가 실제 조회 패턴과 맞는가? (쓰기 비용 포함)
- [ ] 대량 데이터에서 성능 저하 없이 운영 가능한가?

### 3-6. 마이그레이션/릴리즈 안전성

- [ ] 무중단(또는 저중단) 마이그레이션 전략이 있는가?
- [ ] 기존 데이터 백필 계획과 검증 방법이 있는가?
- [ ] 롤백 가능 여부와 불가능 시 대응책이 정의됐는가?
- [ ] 애플리케이션 배포 순서와 스키마 변경 순서가 충돌하지 않는가?
