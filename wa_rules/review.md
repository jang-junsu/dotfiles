# PR 리뷰 체크리스트 (범용)

이 문서는 특정 기능/기술스택에 종속되지 않는 범용 PR 리뷰 기준이다.  
목표는 "동작함" 확인을 넘어, 품질/안정성/유지보수성/운영성까지 함께 검토하는 것이다.

## 0. 리뷰 원칙

- 변경의 목적(Why)과 범위(Scope)를 먼저 이해하고 구현(How)을 본다.
- 코멘트는 가능하면 "문제 -> 영향 -> 제안" 순서로 남긴다.
- 취향보다 기준(정확성, 안전성, 일관성, 비용)을 우선한다.
- 큰 리스크부터 우선순위를 두고 코멘트한다.

## 1. 성능

- [ ] N+1 쿼리 가능성이 없는가?
- [ ] 반복 루프 내 DB/외부 호출을 줄일 수 있는가?
- [ ] `IN` 절/배치 조회/사전 로딩으로 왕복 횟수를 줄일 수 있는가?
- [ ] 메모리 사용량(대량 데이터 로드, 불필요한 복사)이 과하지 않은가?
- [ ] 성능 개선 제안 시, 실제 병목 지점과 측정 기준이 있는가?

## 2. 설계/아키텍처

- [ ] 책임이 적절한 위치와 레이어에 배치됐는가? (응집도 높고 결합도 낮음)
- [ ] 비즈니스 규칙은 가능한 도메인 모델/서비스에 위치하는가?
- [ ] 공통 로직은 재사용 가능한 구조로 추출됐는가?
- [ ] 트랜잭션 범위가 적절한가? (원자성 필요 구간만 묶기)
- [ ] 각 처리의 독립성과 멱등성을 고려해 트랜잭션을 과도하게 쓰지 않았는가?
- [ ] 정상 흐름에서 의도한 결과가 항상 보장되는가?
- [ ] 예외/오류/빈 입력/경계값 처리 누락이 없는가?
- [ ] 시간/날짜/타임존/정렬/중복 등 취약 지점을 다뤘는가?
- [ ] 조건 분기 간 모순이나 도달 불가능 코드가 없는가?

## 3. 코드 일관성과 규약

- [ ] 네이밍, 코드 스타일, 에러 처리 방식이 프로젝트 컨벤션과 일치하는가?
- [ ] 유사 기능/파일과 스타일(에러 처리, 로그 형식, 함수 구조)이 일관적인가?
- [ ] 타입/참조 방식(예: protobuf 상대/완전 수식)이 기존 코드와 충돌하지 않는가?
- [ ] 하드코딩 대신 설정값(env/config) 사용 원칙을 지켰는가?

## 4. 구현 완전성

- [ ] 연관 범위 전체를 다뤘는가? (한 군데만 고치고 다른 경로 누락되지 않았는가)
- [ ] 기존 유스케이스를 깨뜨릴 가능성이 있는가?
- [ ] 기본값/기본 동작 변경 시 영향 범위를 확인했는가?
- [ ] 실패 시나리오(네트워크, 권한, 중단, 재실행)에서 안정적인가?
- [ ] 경계값/예외 케이스(빈 데이터, 대량 데이터, 중복 데이터)를 고려했는가?
- [ ] 부분 대응이라면 TODO/제약/후속 작업이 명확히 남아 있는가?
- [ ] "지금 가능한 최소 변경"과 "궁극적 구조"를 구분해 설명했는가?
- [ ] 임시 구현이라면 제약과 후속 계획이 명시됐는가?
- [ ] 문서(README, 운영 가이드, 사용법)와 실제 동작이 일치하는가?
- [ ] 사용되지 않는 변수/함수/분기가 남아 있지 않은가?
- [ ] 도메인 용어와 실제 구현이 일치하는가?
- [ ] 모니터링/알림/운영 문서 업데이트가 필요한가?

## 5. 실용성/유지보수성

- [ ] 향후 수정 시 오해를 부르는 표현/구조가 없는가?
- [ ] 변경된 동작이 팀원들이 쉽게 재현 가능한가?

## 6. 데이터/상태 안전성

- [ ] 파괴적 작업(삭제/갱신)은 안전장치가 있는가?
- [ ] 상태 변경이 원자성/일관성을 필요로 하는 구간에서 보장되는가?
- [ ] 재시도 가능성/중복 실행 안전성을 고려했는가?
- [ ] 실패 시 부분 적용 상태를 어떻게 처리하는지 명확한가?

## 7. 장애 대응/복구 가능성

- [ ] 실패 시 즉시 원인을 파악할 수 있는 로그/메시지가 있는가?
- [ ] 일시 오류와 영구 오류를 구분해 대응하는가?
- [ ] 복구 절차(수동 조치 포함)가 사용자 관점에서 이해 가능한가?

## 8. 테스트/검증 가능성

- [ ] 핵심 시나리오(정상/실패/취소/재시도)가 검증되는가?
- [ ] 테스트가 어렵다면 대체 검증 방법이 제시됐는가?
- [ ] 검증 결과를 다른 사람이 재현할 수 있는가?

## 9. 승인 전 최종 질문

- [ ] 지금 머지해도 기능/운영 리스크를 수용 가능한가?
- [ ] 지금 승인해도 운영/개발 생산성 측면에서 이득이 분명한가?
- [ ] 이 변경이 팀 생산성과 코드 품질에 실질적으로 이득인가?
- [ ] 이 변경은 3개월 뒤 다른 사람이 봐도 의도를 이해할 수 있는가?
- [ ] 장애 발생 시 탐지/원인 파악/복구가 가능한가?
- [ ] 같은 문제를 다시 수정하지 않도록 구조적으로 해결했는가?
